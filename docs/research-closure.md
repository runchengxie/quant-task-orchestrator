# Research and operations closure

[简体中文](research-closure.zh-CN.md)

Version 0.4 adds immutable Codex receipt observation, frozen Research tool
snapshots, opt-in read-only Codex tool profiles, recovery rehearsals and scheduler
migration preflight. The existing owner boundaries and read-only GUI remain.

## Agent evidence and tools

`codex_task` accepts `action: observe` with the exact `session_id` and `receipt`.
Its start, inspect and cancel operations read only those pinned receipt/event
bytes and never execute a model command. The configuration, executable, prompt
and receipt identities remain bound. Separate workflow steps can attach each
turn; token totals deduplicate the same owner-plan/key/turn across workflows.

A separately authorized live acceptance completed one new session and two calls
in approximately 45 seconds. The second completed turn retained the exact session
and correctly recalled a random marker generated by the first turn. Usage totals
matched both receipts. This established tool-free resume, not model tool use.
Observed-token limits gate later admission; they are not hard in-flight caps.

The Research Owner provides `research.tool-profile/v1` through JSON CLI and stdio
MCP. Four fixed tools read exported evidence, plans, Runtime status snapshots and
artifacts by handle. Each profile/resource is hash-bound. Arbitrary caller paths,
shell, writes and submission are absent. Runtime status is a snapshot, not a live
query. Approved job submission retains the existing campaign owner interface.

For Codex, opt in with `research.codex-task/v2`, retaining the v1 fields and adding
`tool_profile`, `tool_profile_sha256`, `tool_gateway_sha256` and
`tool_python_sha256`. The Owner advertises `research-read-only` and enforces a
32-call ceiling per turn. V1 remains tool-free. Isolated MCP protocol/configuration
and event tests do not establish real model tool-call acceptance.

The coordinator's `research_snapshot` adapter has exactly `kind`, `command`,
`profile`, `expected_profile_sha256` and `handle` (plus optional `owner_revision`).
It invokes the gateway's `--handle` CLI, binds content identity and projects no
resource body. Only input integrity is established; embedded claims of PIT or
promotion cannot turn an evidence gate green.

## Research readiness

Retained data was normalized offline through existing data Owner commands.
Four components produced 966,480 rows with owner validation. A separate
`fina_indicator` two-field PIT asset contains 254,356 events across 6,752 symbols.
Sampled strict as-of checks rejected 2020 and pre-observation requests, accepted
observed validity dates, and rejected expired requests. These are component- and
sample-scoped checks, not evidence for every historical sample or strategy.

The four-component PIT build remains blocked on ambiguous company statement
templates. No template was silently selected. Partial failed output has no valid
publication seal and must not be consumed. No production aliases were updated.
Qualified economic research still needs explicit template policy, sufficient
valid study history, execution semantics and independent review.

Installed data, Runtime and report CLIs are tested in one restarted coordinator
DAG. Their isolated synthetic input artifacts establish dependency ordering,
owner reconciliation and report verification. They do not form a financially
qualified study or assert that a prebuilt report was generated from the backtest.
A final qualification step remains blocked on missing evidence.

## Operations

`restore --source BACKUP --sha256 SHA --destination NEW_PATH` checks the digest,
SQLite integrity and store schema, then publishes exclusively to a new path.
It never overwrites the running database. `storage-check --root DATA_DIRECTORY`
reports free space; it neither deletes retained files nor enforces a disk quota.

`migration-check --input REQUEST_JSON` takes schema
`quant.scheduler_migration_request.v1`, `old_owner`, `new_owner`, `old_active`
and `new_active`. It detects overlap and produces a proposal, never a cutover.
Actual timer/registry inventory remains private. A snapshot alone does not prove
shadow execution or rollback readiness; production migration remains blocked
until a specific workload, ownership mapping and acceptance are supplied.

`outbox-preview ID --ledger LEDGER` sends nothing. The local peer receipt protocol
reserves uncertain attempts before transport, reconciles by original ID and never
blindly resends after a lost response. No external network transport or human
recipient is configured. User acknowledgement and delivery receipt are distinct.
See [operations preflight](operations-preflight.md) for details.

## Selected shadow pilot

The selected pilot is read-only data readiness; notifications stay local.
`shadow-check --config CONFIG --expected-config-sha256 SHA --output-root ROOT`
allows only `data` and `raw_observation` adapters and an empty Skill catalog.
It hashes and parses the same bounded configuration bytes. Each run reserves a
new UUID directory containing its own SQLite store, plan and assessment. It
approves only the two fixed read-only owner kinds, never invokes model or compute
adapters, and does not enable a timer or change an existing schedule.

Owner commands remain trusted programs, not an operating-system filesystem
sandbox. Installed-owner acceptance compares the input tree before/after;
production use must retain pinned owner releases. Successful integrity checks
never assert research qualification. Periodic scheduling is deliberately staged
after a successful shadow rehearsal, rather than enabled by this command.
